# Idaho Regional ET Outlook Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a reproducible, no-setup, 20-day Idaho regional outlook that publishes weather-driven ETo, potential crop ET, latest-date ETa analysis, and explicitly conditional ETa scenarios as static map artifacts and machine-readable data.

**Architecture:** Preserve the current Phase 2 public-data pipeline as the evidence base, then add a physically explicit regional-outlook package beside it. A versioned run manifest freezes source vintages, the weather issue time, grid, model configuration, and output checksums; forecast, hindcast, and publishing consume that same manifest. The public map is a static artifact generated by Python, while Helios is deliberately a later consumer of versioned MLET outputs rather than a dependency of the scientific pipeline.

**Tech Stack:** Python 3.9+, NumPy, xarray, netCDF4, rasterio, pyfao56 (vendored source), standard-library JSON/CSV/HTML generation, pytest, NOAA GEFS archives, OpenET, USDA Cropland Data Layer.

## Global Constraints

- Execute from a worktree based on `origin/main` at `f7d14d3ab9263a59827b8cad482e0d94b38b3474` or a later explicitly reviewed remote commit.
- Idaho only for the first release; retain the source weather grid as the forecast grid. Never imply field-scale or parcel-scale 20-day skill.
- Publish all 20 days as ensemble distributions (`p10`, `p50`, `p90`), not deterministic point forecasts.
- Define `ETo` as daily ASCE standardized short-reference ET; retain all units as `mm/day`.
- Define `potential_et_c_mm` as `Kc × ETo` under ample water; it is not actual ET.
- Publish observed satellite ET only as `eta_analysis_mm` with an explicit observation date and latency.
- Publish future ETa only as a named, conditional scenario: `eta_well_watered_mm` or `eta_no_irrigation_mm`. Do not expose a generic field called `actual_et_forecast`.
- Use real public source data for all scientific runs. Tiny deterministic test fixtures are permitted only to verify software behavior and must not enter an evaluation report or training set.
- Do not commit raw source rasters, API credentials, private field data, or generated operational output. Commit source registries, checksums, fixture data, and reproducible commands only.
- Preserve Phase 2 commands and results. New code must not reinterpret Phase 2 as operational forecast validation.
- No Helios runtime import, network call, or deployment work in this plan. The sole integration seam is a documented versioned MLET output schema.
